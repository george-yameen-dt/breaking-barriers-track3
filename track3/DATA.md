# Data

Synthetic data only. No operator logs, no customer data. The network telemetry is generated by the Viavi AI RAN simulator.

| Data | Source | Licence | How it is made |
|---|---|---|---|
| Cell network telemetry (phones, cells, KPIs) | Viavi AI RAN (AI-RSG) 4-cell scenarios `team04-track3-4cell-healthy`, `-powercut` and `team04-track3-live` (a copy of `-powercut` with a 20-minute duration), built from the organisers' `maveric_4cell` sample | provided by the hackathon organisers; no separate licence text came with the sample | `scenarios/twin/healthy.py` builds the scenarios (phone targets 2+1 Mb/s, S3 commercial power failure at 180 s); `scenarios/twin/run8.py` reads the run and sends one record per cell per minute to Dynatrace |
| Critical-cell labels (hospital, emergency dispatch) | `scenarios/twin/critical-cells.json` | ours | hand-written and **synthetic**: Viavi has no notion of a critical cell |
| Detector thresholds (QoS below 90, phones without service above 4, edge RSRP below -125 dBm, cell enabled below 1) | Dynatrace tenant yqs73977 | n/a | chosen from the healthy and fault KPI ranges of the saved runs (healthy QoS 100, phones without service at most 1.7, RSRP p10 at least -115; fault: S4 QoS 28, 8.7 phones, -134 dBm; S3 dark) and declared in `evidence/declared/<run_id>.json` before the run |
| Dynatrace problem facts for a run | Dynatrace tenant yqs73977 | n/a | `tools/collect_dynatrace.py` copies them into the run's `dynatrace_evidence` record |
| Earlier cell simulator (runs of 2026-11-01 and 2026-11-02 only) | mobile-env, scenario `mobile-medium-central-v0` (github.com/stefanbschneider/mobile-env) | MIT | the simulator was removed from this repo (git history); `scenarios/faults/*.json` and `scenarios/swarm-layout.json` keep those runs rebuildable |
| Incident scenario | `scenarios/incident-v2-cutoff.json` | ours | hand-written. Its SHA-256 is the `test_set` in the registry, signal and promotion declarations |
| Swarm faults and layout | `scenarios/faults/*.json`, `scenarios/swarm-layout.json` | ours | hand-written. Their SHA-256 is in every swarm run's declaration |
| Swarm policies | `policies/swarm.cedar` (the earlier approval-based version is archived by hash in `policies/versions/`) | ours | hand-written. Its SHA-256 is in every swarm run's declaration |
| Tool registry | `policies/tools.json` | ours | the dtctl and Viavi tools the agents may call; `./track3.sh setup` registers them |
| Promotion policies | `policies/promotion.cedar` | ours | hand-written. Its SHA-256 is in every promotion run's declaration |
| Agent prompt versions | `prompts/<agent>/<version>.txt` | ours | `v1` is the running prompt (`incident.DIAGNOSE`, byte-identical, checked by a test). Each candidate's SHA-256 is in its registry item and its promotion declaration |
| Business intents | `intents/*.json` | ours | hand-written thresholds and weights for the outcome score (`coverage_first` for voice, `throughput_first` for video) |

## Model outputs we rely on

Every model call is recorded in `evidence/runs/<run_id>/records.jsonl`, in CloudWatch Logs and in DynamoDB. Each record (`kind: model_call`) carries:
- `model_id`
- `request_id` (the Bedrock request id)
- `prompt_sha256` (the system prompt plus the user prompt)
- `output_sha256`
- the first 2,000 characters of the output

The agents' prompts live in `agents/prompts/*.md` (their SHA-256 is in each run's `run_start` record); the judge's prompt is `JUDGE` in `agents/orchestrator.py`.

| Role | Model | Family |
|---|---|---|
| Orchestrator, coverage, availability, risk critic | `openai.gpt-oss-120b-1:0` | OpenAI gpt-oss |
| Capacity specialist | `openai.gpt-oss-20b-1:0` | OpenAI gpt-oss |
| Earlier network agent, change agent (runs of 2026-11-01) | `openai.gpt-oss-120b-1:0` | OpenAI gpt-oss |
| Independent judge | `us.anthropic.claude-haiku-5-5` | Anthropic (different family from the agents) |
